# akarin 日々の記録

日々の出来事は `records/entries.json` に蓄積し、`diary.html` で日付順に表示する。学校の指導計画は `learning.html` にあり、2026年10月に受け取った資料を基準にしている。日々の記録と指導計画の評価を混同しない。

## チャットで記録を追加する

新しいチャットでは、例えば次のように依頼する。

> GitHubの sususunosusumu/akarin の records/README.md を読んで、日々の記録を追加してください。11月○日、学校では……。家では……。

チャットの発言をそのまま自動保存する仕組みではない。GitHubを操作できるアシスタントが、以下の手順で整理・保存する。

1. 最新のこの説明と `records/entries.json` を読み、既存記録・形式・SHAを確認する。
2. 出来事の日付を `date` に記入する。記録を追加した日時 `created_at` と分ける。日本時間を使う。「今日」はチャット時点の日本の日付へ変換する。年や日付が曖昧で判断できない時だけ確認する。
3. 学校から聞いた内容、家庭で観察した内容、寄宿舎から聞いた内容を分ける。ユーザーが話していない出来事・気持ち・診断・原因・成果を補わない。
4. 氏名、学校名、職員名、学年・組、所在地、連絡先、生年月日など、所属・本人の特定につながる情報は除く。呼称は akarin。原画像・原文ファイル・未加工の発言は保存しない。
5. 観察・伝聞は `observations`、ユーザーの考えは `reflections`、今後の確認・相談は `follow_up` に分ける。アシスタントの解釈を追加する場合はその由来を明記し、観察事実へ混ぜない。
6. UUID等で一意の `id` を付ける。既存と同日の追記も別IDで保存できるが、重複する出来事は二重登録しない。訂正は該当IDの内容と `updated_at` を更新し、無関係な記録を変更しない。
7. JSONの構文・日付・必須項目・IDの一意性と、個人名や所属情報が残っていないことを確認する。
8. 最新SHAを使ってJSONを更新する。競合したら読み直して既存の追加分を保持する。保存した日付・要約・リンクをユーザーへ伝える。空の項目を埋めるためだけに質問しない。

## データ形式

ルートは `schema_version`、`subject`、`updated_at`、`entries`。`updated_at` は最後に保存した日時（ISO 8601、+09:00）。記録ゼロの場合はnull。

各entryの必須項目：

| キー | 形式・意味 |
| --- | --- |
| id | 一意の文字列 |
| date | 出来事の日付 YYYY-MM-DD |
| title | 内容が分かる短い見出し |
| summary | 全体を短くまとめた文章 |
| observations | 下記の観察オブジェクトの配列 |
| reflections | `{ text, source }` の配列。なければ空配列 |
| follow_up | 次に確認・相談する事項の文字列配列 |
| tags | 「意思表示」「入浴」「切り替え」等の文字列配列。診断等を推測して付けない |
| created_at | 記録作成日時、ISO 8601 |
| updated_at | 最終編集日時、ISO 8601 |

観察オブジェクト：`{ setting, source, text }`。

- `setting` は `school`（学校）、`home`（家庭）、`dormitory`（寄宿舎）、`other`（その他）。
- `source` は「学校からの連絡（保護者談）」「保護者の家庭での観察」「寄宿舎からの連絡（保護者談）」等。誰の観察・報告かを個人名を使わず示す。不明な時は「情報源未確認」とする。
- `text` は読みやすく整えた出来事。誰の発言・伝聞か、援助の有無等の条件を保つ。

## 最近の様子をまとめる場合

JSONの最新データを読み、対象期間を明示する。学校・家庭・寄宿舎ごとの出来事、繰り返し見られた姿、役立った支援、未確認のことを分ける。根拠となる日付とIDを付ける。記録のない日は「問題なし」「欠席」「できなかった」と扱わない。少数の記録から能力や傾向を断定しない。2026年10月の資料と比べる時は、その資料の基準月を明記し、新しい出来事を計画の正式評価と見なさない。
